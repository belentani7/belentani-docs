# Guía de Seguridad

## Principios

1. **Defensa en profundidad**: Múltiples capas de protección
2. **Mínimo privilegio**: Acceso mínimo necesario
3. **Cifrado por defecto**: TLS 1.3, datos en reposo
4. **Auditoría continua**: Logs, alertas, revisiones
5. **Respuesta a incidentes**: Plan definido, roles claros

## Gestión de Secretos

### NO HACER

- Commitear .env, .env.local, *.pem, *.key
- Hardcodear passwords, API keys, tokens en código
- Compartir secrets por chat, email, issues
- Usar mismos secrets en dev/staging/prod

### HACER

- .env en .gitignore (verificado en CI)
- **Gitleaks** en pre-commit + CI
- **Dependabot** para actualizaciones de seguridad
- **Vercel/GitHub Secrets** para deploy/runtime
- **Rotación periódica**: 90 días máximo
- **Scope mínimo**: Tokens con permisos mínimos necesarios

## Autenticación y Autorización

### JWT Best Practices

- **Algoritmo**: RS256 (asimétrico) preferido sobre HS256
- **Expiración**: Access token 15-30 min, Refresh token 7-30 días
- **Claims**: sub, exp, iat, scopes, aud, iss
- **Validación**: Siempre verificar firma, expiración, audience, issuer
- **Revocation**: Blocklist en Redis para logout/invalidación

### Rate Limiting

- **Por IP**: 60 req/min, 1000 req/hora (configurable)
- **Por usuario autenticado**: Límites más altos
- **Endpoints críticos**: Login/register más restrictivos
- **Headers**: Retry-After, X-RateLimit-Limit, X-RateLimit-Remaining

## Seguridad de Dependencias

### Auditoría Continua

- **Dependabot**: Grouped updates, PRs automáticos
- **Major versions**: Ignoradas por defecto (requieren review manual)
- **npm audit / pip-audit**: En CI semanal
- **License check**: Solo licencias aprobadas (MIT, Apache-2.0, BSD)

### SBOM (Software Bill of Materials)

```bash
# Generar SBOM
syft packages dir:. -o spdx-json=sbom.spdx.json

# Verificar vulnerabilidades
grype sbom:sbom.spdx.json
```

## Seguridad en CI/CD

### GitHub Actions

- **Permisos mínimos**: permissions: { contents: read }
- **Secrets**: Solo en secrets, nunca en logs
- **Pin actions**: actions/checkout@v4 (no @main)
- **Reusable workflows**: Para compartir lógica

### Code Scanning

- **CodeQL**: Análisis estático semanal
- **SAST**: Reglas personalizadas para patrones inseguros
- **Secrets scanning**: Gitleaks + GitHub secret scanning

## Protección de Datos

### En Tránsito

- **TLS 1.3**: Obligatorio en producción
- **HSTS**: Strict-Transport-Security: max-age=31536000
- **Certificate Transparency**: Monitoreo de certificados

### En Reposo

- **Base de datos**: Cifrado nativo (PostgreSQL TDE, AWS RDS encryption)
- **Backups**: Cifrados, en región diferente
- **Secrets manager**: AWS Secrets Manager / HashiCorp Vault

### PII (Datos Personales)

- **Minimización**: Solo recoger lo necesario
- **Pseudonimización**: IDs en lugar de emails en logs
- **Derecho al olvido**: Endpoint DELETE /me con cascade
- **Retención**: Política documentada, auto-limpieza

## Headers de Seguridad

```python
# FastAPI middleware
@app.middleware("http")
async def security_headers(request, call_next):
    response = await call_next(request)
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["X-Frame-Options"] = "DENY"
    response.headers["X-XSS-Protection"] = "1; mode=block"
    response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"
    response.headers["Content-Security-Policy"] = "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';"
    response.headers["Permissions-Policy"] = "camera=(), microphone=(), geolocation=()"
    return response
```

## Logging y Auditoría

### Logs Estructurados

```python
import structlog

logger = structlog.get_logger()

# Bueno
logger.info("user_login", user_id=user.id, ip=request.client.host, success=True)

# Malo (PII en logs)
logger.info("user_login", email=user.email, password="***")  # NO
```

### Eventos a Auditar

- Autenticación: login, logout, failed attempts, password reset
- Autorización: permission denied, scope escalation
- Datos: create, read (sensitive), update, delete
- Admin: user management, config changes, deployments
- Seguridad: rate limit exceeded, blocked IPs, scanning attempts

## Respuesta a Incidentes

### Niveles de Severidad

| Nivel | Descripción | SLA Respuesta | SLA Resolución |
|-------|-------------|---------------|----------------|
| P0 - Crítico | Brecha de datos, servicio caído | 15 min | 1 hora |
| P1 - Alto | Vulnerabilidad activa, degradación | 1 hora | 4 horas |
| P2 - Medio | Vulnerabilidad potencial, degradación menor | 4 horas | 24 horas |
| P3 - Bajo | Mejora de seguridad, hardening | 24 horas | 1 semana |

### Runbook Básico

1. **Detectar**: Alertas (PagerDuty, OpsGenie), reportes usuarios
2. **Triage**: Confirmar, clasificar severidad, asignar owner
3. **Contener**: Bloquear IP, revocar tokens, mantenimiento
4. **Erradicar**: Parchear, rotar secrets, limpiar
5. **Recuperar**: Restablecer servicio, verificar
6. **Post-mortem**: Análisis raíz, acción correctiva, documentación

## Checklist de Seguridad Pre-Deploy

- [ ] Gitleaks pasa
- [ ] Dependabot alerts resueltas
- [ ] CodeQL analysis pasa
- [ ] npm audit / pip-audit sin critical/high
- [ ] Rate limiting configurado
- [ ] CORS restrictivo
- [ ] Headers de seguridad presentes
- [ ] Rate limiting en endpoints críticos
- [ ] Logs sin PII
- [ ] Secrets solo en vault/secrets manager
- [ ] Backups cifrados y probados
- [ ] Rollback plan documentado
